# How do you decide what to work on when no one is directing you?

My instinct is to find the one thing that makes everything else easier. That's usually structural: if I sense the codebase is heading toward a problem I'll address it early, even though it produces no visible progress. Small signals — a minor bug that took longer than expected to trace, a component that's harder to extend than it should be — point to structural weaknesses before they become obvious. Ignoring them is easy because there's no reward for avoiding a problem that doesn't exist yet. But I've seen what happens when they're left.

The other priority is the next significant step toward the spec — broad brushstrokes before detail. On Folio I started with the AI API integration rather than the UI, because the shape of the responses determined what the interface could look like. That order prevented me from building a UI against assumptions that turned out to be wrong. On Nexus I'd pick the feature that would make the most of the structure I'd already laid down.

How much I own changes the scope of this thinking. On a project I own I make high-level decisions on structure and features. Within someone else's project I apply the same logic to my slice of the work — following the conventions of the wider project rather than imposing my own.
