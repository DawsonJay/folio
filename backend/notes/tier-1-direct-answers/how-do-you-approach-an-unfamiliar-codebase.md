# How do you approach an unfamiliar codebase?

I start with the running app, not the code. Click around, understand what it is and what it's supposed to do. Then skim the codebase: what technologies are being used, how the pieces roughly fit together, how components are organised so I can navigate. Only then do I zero in on the area I need to work in.

When I make changes I aim for consistency with the surrounding code — existing components where applicable, matching conventions for naming, commenting, and styles. The goal is for my addition to look like it was always there, just slightly more polished.

I also keep notes. A good example was a legacy page at BriefYourMarket (worked on during my time at Nurtur) that had been custom-built for a large client. After being given one job on it I became the go-to person whenever that page needed work. I kept a folder with the structure, conventions, and problems I'd already solved so that when I came back to it weeks or months later I could get back up to speed quickly. Moving between projects is disorienting and memory is unreliable — notes are cheaper than rediscovering everything from scratch.
