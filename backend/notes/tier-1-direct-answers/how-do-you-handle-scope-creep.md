# How do you handle scope creep?

I've managed scope on multiple client projects during freelance work and on team projects at Nurtur. My approach is to define the MVP clearly and use a backlog for everything else. The MVP is the bare minimum that delivers core value with structure to expand later. Not just the smallest version we can ship, but the smallest version that solves the fundamental problem and can support future features without rebuilding from scratch.

I dealt with scope creep a lot during freelance work. One client kept adding features that sounded good - every conversation brought new "wouldn't it be nice if..." ideas that would have ballooned the project indefinitely. I defined a clear barebones version with a timeline, reasoned that we'd focus on this foundation first, and added extras to a backlog for later if she still wanted them. The key was structuring the MVP so it could expand to allow those features.

This approach worked because it gave her a clear timeline to the first working version while acknowledging her ideas had value. Many features she thought were essential early on turned out not to matter once she could actually use the core product. The backlog prevented scope creep during critical initial development.

When scope starts expanding, I make the tradeoff explicit: adding that feature means either a longer timeline or cutting something else — which do you prefer? That framing usually focuses the conversation quickly. Features that can't survive "what problem does this solve?" don't belong in the MVP. Most of the time, once someone can actually use the core product, the extras they thought were essential turn out not to matter.
